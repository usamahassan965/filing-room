Filing_Agentic_RAG · build plan v1

Nine gates to a shipped filing analyst

An agentic RAG system that answers multi-hop questions over SEC filings by routing numeric sub-questions to SQL over XBRL and narrative ones to hybrid text search — with every figure recomputed, every claim cited, and every run traced. Gate-based, not date-based: each milestone has a definition of done that a command can verify. You do not advance on a gate you cannot prove.

The constraint comes first

Everything downstream is shaped by the Gemini free tier: an OpenAI-compatible endpoint at generativelanguage.googleapis.com/v1beta/openai/, a per-model request ceiling that ranges from roughly 10 rpm on the chat model to 100 on embeddings, and a daily request cap on top of it. Design for it on day one and it never bites you; discover it in week four and you rebuild.

Seven decisions that fall out of the rate limit

  1. One adapter, no exceptions. Every model call goes through a backend module — llm/gemini.py today. Rate limiter, retry, and cache live there and nowhere else. No module ever calls a provider directly, which is what makes a provider swap a file rather than a refactor.
  2. One limiter per model, not per provider. Chat allows a tenth of what embeddings do. A single shared limiter would throttle the whole indexing run to the speed of the slowest model in the registry, and you would blame the network.
  3. Cache by content hash, aggressively. A repeated eval run should cost close to zero API calls. This is what makes ablations affordable — you are re-scoring cached generations, not regenerating them.
  4. Batch the embeddings. Indexing is the single biggest credit consumer. Do it once, cache the vectors to disk, and never re-embed an unchanged chunk.
  5. Judge suite runs nightly, not per commit. CI gets the deterministic metrics only — free, fast, non-flaky. LLM-judged metrics run on a schedule.
  6. Model IDs live in a registry. Hosted model IDs are retired on the vendor's schedule, not yours. Put them in config.py so a retirement is one line, not a grep across the repo. This is the decision that paid for itself first — see M0.
  7. Wire the local fallback in M0, not in a panic. Same adapter interface, Ollama behind it. If credits run out mid-week you switch an env var and keep working at lower quality instead of losing days.

The stack

Well-worn Python packages throughout. Nothing exotic, nothing that will be unmaintained in six months — every choice is one you can defend in an interview.

What actually happenedBoth bail-outs fired, in the same gate. NVIDIA NIM was the original provider; its account verification proved impassable, so the whole provider was swapped for Gemini plus a local cross-encoder — one new backend file and one registry block, with the limiter, cache, tracing and every test carried over untouched. Then on the first live run every Gemini 2.x chat ID answered 404, “no longer available to new users”, while embeddings kept working: two more registry lines, no code. The gate's own premise is what made both cheap.

One correction the run forced, now in the code: a model listing is not a probe. ListModels returned an ID this key could not call, so filing probe issues a real request per ID instead of trusting the catalog — and never pins a *-latest alias, since one answered 503 while the pinned ID was fine.

Writing the fallback’s tests turned up something the risk register had wrong. “Flip LLM_BACKEND and keep working” is true for chat and false for retrieval: Gemini embeds at 1536 dims and nomic-embed-text at 768, and even at equal width they are different vector spaces where cosine means nothing. That is a silent failure — an index queried with the other backend’s vectors returns neighbours, just wrong ones. So the claim is narrowed above, M3 keys each collection by backend + model + dim so a swap is a startup error, and the finding is an assertion in the test file rather than a sentence in a doc, because prose does not fail a build.

A late finding against this gate, and it invalidated the gate rather than a line of it. filing smoke passed 5/5 at http calls: 0, cache hits: 4 — the cache is keyed on the payload, and the payload had not changed since the first run of the day, so the command was replaying old answers. A revoked key, a retired model ID or an exhausted free tier would all still have printed 5/5, which is the one failure a smoke test exists to catch. Chat and embed now carry a fresh run marker and must miss, asserted rather than hoped for; the dedup check then repeats the marked prompt, so it proves dedup on an entry this process wrote seconds earlier instead of on whatever was already warm. Rerank keeps its cache on purpose — it is a local forward pass on every backend, so no credential can hide behind it. The cost is two live calls per run, which is the price of the command meaning anything.

If it breaksEDGAR returns 403 → you forgot the User-Agent header with a real contact address. If it throttles, back off and resume from the manifest; never restart a download run from scratch.

What actually happenededgartools was dropped for raw httpx. It maintains its own local filing store, and a gate whose whole premise is the manifest is the source of truth cannot also have a second one; the EDGAR contract is four endpoints, and it is the part worth showing. Two hazards inside it are invisible until they cost you a corpus. filings.recent caps at ~1000 submissions — a heavy Form-4 filer burns that in under three years, so five years of 10-Ks can sit entirely in the overflow chunks under filings.files. And filtering on a fiscal-year label is filtering on a company convention: the year ending 2024-01-31 is Walmart's FY2024 while the year ending 2024-02-03 is Target's FY2023. The corpus filters on period end instead, and the five retailers are in the universe precisely so that divergence stays visible.

The gate then caught something none of its original four checks would have. XOM contributed zero filings and everything still passed. SEC's company_tickers.json maps a ticker to whoever trades under it today — for XOM a registrant created in a holding-company reorganisation, whose first filing postdates the entire window, while the history sits under a CIK that now carries no ticker at all. Resolution succeeded; the corpus was silently short one company's five years. Nothing errored, and 387 filings across 20 companies looked healthy in every total. The fix is two lines of YAML pinning the CIK — but the real fix is the per-company coverage check the gate now runs, because a corpus-wide total can never see a hole inside one company. An aggregate that passes is not evidence that its parts did.

The resume path was proved by accident: the first run was killed partway through, and the restart fetched the 35 missing filings in 62 requests instead of re-downloading 387 in ~600. The manifest row goes in only after the bytes land, which is what makes that safe.

Structured store

Every number the system will ever state, in SQL, with a link back to the filing that reported it. No LLM touches arithmetic after this gate.

Build

  • facts table: cik, taxonomy, tag, unit, period_start, period_end, span, val, accn, filed — 514,649 rows, 2,827 concepts
  • companies and filings dimension tables, copied in rather than attached
  • Metric registry: 25 metrics, human name → us-gaap tag(s) → SQL expression, resolved per company
  • Derived views: gross/operating/net margin, ROE, ROA, D/E, FCF, YoY growth, CAGR

  • Uniqueness holds on (cik, taxonomy, tag, unit, period, accn) — 0 duplicates. Not on segment: companyfacts returns consolidated figures only and carries no segment field, so the original key named a column that cannot exist
  • 50 randomly sampled facts checked against the source filing — 49 found across 45 documents; the one miss is a Pfizer tax line that lives in the XBRL attachment and not the readable 10-Q
  • 10 hand-written numeric questions answered exactly by SQL, no LLM in the loop — 10/10
  • Derived metrics match a manual calculation for 3 companies — 570 values over 57 fiscal years, recomputed longhand in Python, zero disagreement
duckdbpolarspanderapytest

If it breaksXBRL segment dimensions are genuinely messy. v1 scope is consolidated totals only — document the exclusion in the README rather than burning a week on axis normalisation.

What actually happenedThe bail-out was never needed, because the premise was wrong in the useful direction: the companyfacts endpoint carries no segment dimension at all. It is consolidated-only by construction, so both the uniqueness key and the escape hatch named a column that does not exist. Segment data would mean parsing the XBRL attachments, which is a different gate.

Three properties of this data cost more than the loading did. A tag is not a period. NetIncomeLoss carries quarters, halves, nine-month stubs and full years under one name; summing the tag over a year triple-counts it. Every fact is therefore classified by span against the nearest canonical length, with a 25-day tolerance chosen because 4-4-5 retailers report 168-day halves and 252-day nine-months that no round range admits. A filing's fiscal-year label is not its facts' periods — fy/fp disagree with year(period_end) on 54.9% of rows, so they are stored as filed_fy/filed_fp and never used as a key. And the declared UNIQUE constraint is not the check: SQL treats NULLs as distinct and period_start is NULL for all 195,325 instants, so the constraint silently exempts 38% of the table. The gate runs a GROUP BY, which does treat NULLs as equal.

Numbers change after they are published: 11,359 period-keys (4.3%) carry more than one value. Both are kept, facts_current picks the latest filing, and restatements exposes the movement — a restatement is a finding, not an error. But “latest wins” is right for a fact and wrong for a statement: a revision moves a set of lines together and a company re-tags only the years it still presents, so taking the newest value of each line independently can assemble a balance sheet out of two filings that balances in neither. Costco's FY2014 assets were revised in the FY2016 10-K without its liabilities being re-tagged. The identity check therefore reads one accession at a time — and then closes on 1,717 balance sheets with zero violations.

The ten questions were meant to be a formality and scored 5/10 on the first run, two of them real defects. AbbVie and Pfizer appeared to do no R&D: they report ResearchAndDevelopmentExpenseExcludingAcquiredInProcessCost, which the registry did not list — a fourth failure class, near-synonyms that are not synonyms, which yields wrong answers rather than missing ones. And 15 balance sheets did not balance, because the identity has four right-hand terms and the registry had two: total equity including NCI, the pre-ASC-810 MinorityInterest line, and mezzanine equity that belongs to neither side. That also forced a second resolution rule: coverage-first is right for a tag succession (19 of 20 companies switch revenue tags at ASC 606 and the series must survive), but registry-priority is right for near-synonyms — ranking equity by coverage had put ten companies on one definition of equity and ten on the other, so the ROE denominator meant different things depending on the ticker.

Unstructured store

The narrative half: section-aware chunks that never lose their character offsets, indexed twice and fused.

Build

  • Docling parse → blocks, cached to parquet so you parse each filing exactly once

Definition of done

  • 100% of filings parsed or explicitly quarantined with a written reason — 407/407, zero quarantined
  • 200 random chunks: offsets resolve back to identical source text — 200 across 149 filings, zero differ
  • Re-indexing an unchanged corpus costs zero embedding calls — 32,218 already present, 0 HTTP calls
  • recall@50 ≥ 0.85 on a 30-question smoke set — 100%, and see below for why that is a weaker result than it looks
  • Reranking measurably improves precision@5 on that same set — 0.687 → 0.693, a pass that is inside the noise

If it breaksDocling is slow on 300-page filings — that is expected, parse once and cache. If Docker is painful on Windows, swap Qdrant for embedded LanceDB behind the same store interface; the rest of the codebase should not notice.

What actually happenedThe bail-out that fired was one the register never listed. The free tier's wall is documents per day, not requests per minute. batchEmbedContents bills each text in the batch as its own embed_content request against a 1,000/day cap — a 32-chunk batch spends 32 of the day's thousand — so the first build died at exactly 997 cached rows. Rate limits have pacing solutions; a daily cap does not, and at 1,000/day this corpus indexes once every 33 days, which means the chunker could never be changed again. So the vector space moved onto the CPU: bge-small-en-v1.5, 32,218 chunks in 140.6 minutes at 230 chunks/min, no key and no quota. Generation stayed hosted, because that is one call per answer while embedding is one call per chunk — and only one of those scales with the corpus. EMBED_BACKEND is now a separate setting from LLM_BACKEND for exactly that reason, and the local backend has no chat role at all, so asking for one is a KeyError naming the roles it does have rather than a silent downgrade.

Two of the five checks passed in a way worth reading rather than celebrating. recall@50 of 100% is a weak result wearing a strong number: gold sets here run 21–318 chunks, so landing one of them inside a fifty-candidate window is not a hard task. The statistic with signal is where the first gold chunk lands — rank 1 for 19 of 30 questions, inside the top 5 for 26, worst case 24 — and that is the distribution the floor should have been written against. And the cross-encoder did not earn its latency: 0.687 → 0.693 clears a > 0 gate and means nothing, because the split is 8 questions better, 7 worse, 15 unchanged. The pattern underneath is real though — it gains where fusion did badly and loses where fusion did well. The threshold stays where it was written; moving it after seeing 8–7–15 would be choosing a gate this run happens to pass, which is the one thing a pre-registered criterion exists to prevent. M4's 150 questions are where a delta that size becomes legible.

One process finding, cheaply learned. A gate command nobody has run is not a gate. filing text had two crashing bugs on first execution — a missing constructor argument, and a manifest path joined against the project root instead of the data directory — in code that reads perfectly well and had passed review. Three of its six checks need no index, so they now get run while the two-hour build is still going, which is how both were found with time left to fix them.

Baseline and eval harness

The gate that makes every later claim measurable. Build the naive system you intend to beat, and freeze the questions before you know how the agent behaves.

Build

  • Deliberately naive RAG: fixed 512-token chunks, dense top-5, one LLM call
  • Eval set v1.0 — 150 questions: 80 numeric auto-generated from XBRL with verified gold, 60 narrative with hand-checked gold spans, 10 unanswerable
  • Runner with config hashing and result caching
  • Deterministic metric suite: exact-match, recall@k, nDCG, router accuracy, citation resolution
  • Results written as JSON plus a rendered markdown table

Definition of done

  • python -m filing.eval run --config baseline writes results/baseline.json — 150 questions, 54 seconds, 4 live calls; --config baseline-retrieval writes the no-generator ceiling in 104 seconds for zero calls
  • Eval set tagged v1.0, committed, with a datasheet describing how each slice was built — 150 questions, 260 gold spans, 87 filings, sha256 38ee1f91…, documented in docs/eval-set.md
  • Deterministic metrics complete with zero LLM calls — 127 eval tests, every scoring path driven by a fake backend, and tests/conftest.py now fails any test that opens a socket off this machine
  • A full baseline run fits inside the rate-limit budget and is reproducible from cache — 146 of 150 answers replayed from the content-addressed cache, so a full re-run cost 4 requests against a 15/min model
ragaspytestrichtyperjinja2

What actually happenedThe bail-out clause was written for the wrong risk. The labels did not slip; the chat quota did — to 20 requests a day, not the ~250 the plan assumed. A 150-question run therefore takes eight days, and any re-run takes eight more, which does not merely make the gate slow: the gate asks for a run that is reproducible, and at 20/day it is not.

So the baseline was split at the seam where a RAG answer actually fails. Either the retriever never found the evidence or the generator fumbled evidence it had, and only the second needs a model. baseline-retrieval is the first half: the same retriever, no generator, scored over all 150 questions in 104 seconds for zero API calls. It is not a lesser measurement — it is the ceiling on every number the full baseline can report, since nothing cites evidence it was never shown. The split is enforced rather than trusted: with generation off, every chat field is blanked before the config is fingerprinted, so retrieval numbers cannot arrive under two identities depending on which generator happened to be configured.

The result was low enough to suspect the harness, so the harness was checked before the finding was written down. Handed a chunk's own text as a query the retriever returns that chunk at rank 1, six times of six, at cosine 0.95–0.98; all 260 gold spans are covered by an indexed chunk. The numbers are real: hit@5 of 15.0% narrative and 2.5% numeric. And the more useful number is not hit@10 at all, because hit@10 = 0 covers two opposite diagnoses. filing.eval depth separates them. On narrative questions the system knows which filing to read and not where to look in it — right document at median rank 5, right passage at median rank 24, so hit rises 30% → 55% between depth 10 and 50 and a fuse-and-rerank pipeline has real room. On numeric questions it is not close: median rank 147, and for 45 of 80 the evidence is not in the top 500 of 48,934 chunks. A numeric gold span is six characters — the digits of the figure — inside a 2,048-character slice of a financial statement that is a wall of numbers with no distinguishing prose. Routing numeric questions to SQL was an argument when this plan was written; it is now a measurement, and its size is 2.5%.

Two more defects fell out, both about the harness lying rather than the system failing. The runner cached failures: a 429 became an outcome carrying an error and the cache stored it like a result, so a run built to resume after a rate limit resumed by replaying its own rate limits from disk, permanently. And a test was spending live quota: it passed None for the backend and asserted the cache would serve every question — true on a cache hit, but on a cache miss the runner correctly builds the real client, so an unrelated bug emptied the cache and a hermetic-looking test burned real requests and reported the 429s as ordinary failures. Tests now fail on any socket opened off this machine. Two files went from 121s to 1.9s, nearly all of it retry backoff.

What closed it was reading the gate instead of shopping for a model. The 20-a-day cap belongs to gemini-3.5-flash; gemini-3.5-flash-lite shares none of it, and the gate does not ask for the strongest generator — it asks for a run that fits the budget and reproduces. Flash was disqualified by the gate’s own fourth line, which makes flash-lite a consequence rather than a compromise; the results file names the model, so the weaker generator is stated rather than hidden. The full baseline answers 7.5% exact on numbers, cites something 100% of the time, and abstains on 10 of 10 unanswerables — always confident, rarely right, which is exactly the shape a naive baseline should have. Exact (7.5%) exceeding hit@5 (7.9%’s numeric half, 2.5%) is not a bonus, it is a warning: those answers came from parametric memory, not from the filing.

A third defect, and the worst kind. A 150-question run declared ollama in its config, was fingerprinted, cached and written under llama3.2:3b — and sent all 180 calls to Gemini, because the runner built its client from the environment instead of from the config it had just fingerprinted. It surfaced through a 503 whose wording (“high demand”) could not have come from localhost. The files were deleted rather than relabelled, and a test now binds the constructed backend to the fingerprinted one. The redeeming detail is that the cache is keyed on backend and model, so those calls were always filed under Gemini truthfully — which is why the corrected baseline needed 4 live calls instead of 150.

If it breaksIf the 60 narrative labels slip, ship M4 with the 80 numeric plus 10 unanswerable and backfill narrative during M5. Never block the critical path on labelling — but never start M5 without some frozen baseline number.

M4.5

OFF-PLAN

Interlude

The provider bake-off

M0 claimed that swapping providers is a registry entry rather than a refactor, and nothing had ever tested that claim — the project had run on one hosted provider since the first commit. A claim nobody has tried is a comment, not an interface.

Build

  • Cohere, Groq and OVHcloud added as registry entries behind one OpenAICompatBackend
  • Three eval configs reusing the naive baseline's index, top-5 and prompt unchanged, so the generator is the only variable
  • Chosen for how differently they meter, not for how they benchmark

What it had to show

  • Three providers arrive in one file — llm/openai_compat.py, no CohereBackend, no GroqBackend, zero changes to any caller
  • The ablation is clean, checked rather than asserted — every retrieval metric byte-identical to baseline across all three configs
  • Each free tier's real binding limit measured on a run, not read from a docs page
  • A subset run cannot borrow a full run's filename — --limit writes *.partial.json under its own banner
coheregroqovhcloudhttpx

What actually happenedThe claim held — three providers, one file, no refactor — and the interesting result was the one nobody set out to measure. Free tiers differ more in what they meter than in what they serve. Cohere meters calls (1,000 a month, so a 150-question run is 15% of the month and nine minutes of wall clock). Groq meters tokens per day. OVHcloud meters a shared anonymous pool that belongs to nobody. That shape, not model quality, is what decides whether a gate can be re-run.

Groq stopped the run at question 72 on a cap that appears in no header. Its live x-ratelimit headers say 8,000 tokens per minute and are correct; they say nothing about 200,000 tokens per day, per model, which shows up only in the body of the 429 that ends you — about 47 questions, so a full baseline there is a three-day run. That sharpens M0's lesson rather than repeating it: “probe, don't read the listicle” got the pace right and still missed the binding constraint, because a probe measures what one call is allowed and a run measures what a thousand calls are allowed.

The three generators are separated by almost nothing. Scored on the same 72 questions, gemini-3.5-flash-lite, command-a-03-2025 and gpt-oss-120b differ by 8 points of routing and 6 of citation groundedness — and not at all on exact match: the same four of twelve numeric questions, with every retrieval column identical to the last digit. M4 concluded the retriever is the ceiling; this is that finding arriving from the other direction, and it is why M5 spends its budget on retrieval rather than on shopping for a better model.

Two failures worth the afternoon they cost, both wearing the wrong label. An absent header and an empty one are different requests: the OpenAI SDK insists on an api_key string, and sending OVHcloud a placeholder makes it stop reading the request as anonymous and start reading it as a failed credential — 403 authentication failed on every question, which looks exactly like a key problem and is the precise opposite of one. The header is now stripped at the transport layer, and the proof it worked is that the 403 became a 429. And a 403 is not always about the credential: Groq sits behind Cloudflare, which fingerprints the client before the origin sees the key, so a default Python User-Agent earns 403 Error 1010. Two providers, two 403s, neither of them the key.

Then the ruler turned out to be broken. gpt-oss-120b scored 0% on citations while citing correctly on every answer, because it writes its brackets as U+3010/U+3011 — the CJK lenticular pair — and the parser matched ASCII only. The prompt asks for “bracketed numbers” and never promises a codepoint, so the model kept the contract and the regex did not. Published, that would have been a confident finding about a model, drawn entirely from a measurement error.

The agent graph

The project's actual thesis: planner, router, three retrievers, reranker, grader, and a bounded repair loop.

Build

  • Typed LangGraph state and the unified evidence schema
  • Nodes: plan → route → retrieve{sql, text, graph} → rerank → grade → repair → synthesise
  • Router emits a store choice per typed sub-question
  • Text-to-SQL constrained to the metric registry for v1, free-form only behind a flag
  • Repair budget of 2, then abstain; checkpointing so a failed run resumes
  • One span per node with documented attributes

Definition of done

  • All 150 questions run with no unhandled exception — 150/150, zero errors, 25 minutes, 290 hosted calls
  • Accuracy beats baseline — target ≥ +20 points absolute on the multi-hop slice — +91.3 on the numeric slice, because the frozen set has no multi-hop one; the substitution is below
  • Router accuracy ≥ 0.85 against gold store labels — 0.833, and not rounded up
  • Repair loop provably never exceeds 2 iterations (unit test) — a hard counter and the graph's recursion_limit, both tested
  • One full trace exported to docs/trace_example.json — two, captured in-process and regenerable by command

If it breaksIf the router underperforms, fall back to querying all three stores in parallel and letting the reranker sort it out. Slower and more expensive, but correct — and reporting it as a measured trade-off is stronger than hiding a weak router.

What actually happenedThe bail-out was never needed and the headline is large: 7.5% → 98.8% exact on the numeric slice, 27.3% → 83.3% overall routing, narrative hit@5 15.0% → 40.7%, over the same 150 questions with the same generator, the same refusal token and the same citation contract — imported from the baseline's module rather than restated, so one rule scores both systems. 150 questions, 0 errors, 290 hosted calls, 25 minutes: under two calls a question, which is the budget the design was built to. Plan and route are one call, retrieve/rerank/grade/repair are local and deterministic, synthesis is the second, and an abstention costs nothing.

The 98.8% is partly a tautology, and the honest thing is to say which part. The numeric questions were generated from facts_current and the SQL branch queries facts_current, so a system that resolves the metric and the period correctly is expected to return the same row. What survives that is real but narrower: the router sends numeric questions to the fact store 98.8% of the time, and the templated text-to-SQL layer picks the right row out of near-duplicates that share a tag and differ by period, unit, or a later restatement. What it establishes about retrieval is nothing at all — which is why it is quoted beside a retrieval column that is deliberately empty.

That empty column is the useful kind of empty. A supported citation is one whose chunk overlaps a gold character span, and an XBRL fact has no character span: the value in DuckDB and the number printed in the filing are one fact reached two ways, and only one way carries offsets. So sql and graph routes are excluded from span scoring rather than scored zero, and the scorecard grew a visible ret n column to say so — the agent's 40.0% overall hit@5 is over the 60 questions that actually reached the text store, a subset biased by construction, since the numeric questions in it are exactly the ones SQL could not answer. A text route that retrieved nothing still scores zero, and there is a test for each half, because an exclusion with no floor under it is an excuse. The substitute check is accession-level: 79 of 79 sql-routed answers cite the accession the gold value came from — circular in the same way, but it rules out the failure it was aimed at, which is returning a real number from the wrong filing.

One number on this card moved after it shipped. The numeric slice read 97.5% until M6's verifier turned up a sign bug — in the scorer, not the agent: eval/metrics.py read accounting parentheses but not a leading minus, so a stated loss of −2,701,000,000 that matched the fact store exactly was compared against a profit and marked wrong. It is 98.8% now, one question, and the note that used to read “possible sign convention, uninvestigated” is a regression test.

The router gate is missed, at 0.833 against a bar of 0.85. The numeric slice is 98.8% and the unanswerable slice 100%; narrative at 60.0% is what holds the total under. Most of that is not misrouting. The harness maps any INSUFFICIENT EVIDENCE answer to route="refuse", so a question routed correctly to the text store, retrieved for, and then abstained on because the evidence was thin is scored as a routing failure. The baseline is scored by the identical rule, so the comparison stays symmetric — but the metric is measuring the whole pipeline's confidence and calling it routing. The bar stays where it was written.

And the gate's real win is upstream of every model call. Retrieval was ablated with the generator off — no key, no quota, runs on any machine. Naive dense over 2,048-char chunks gets narrative hit@10 to 30.0%; semantic chunking plus dense+BM25 fused by RRF takes it to 63.3%, and hit@5 from 15.0% to 51.7%. The baseline's ceiling more than doubled before a single token was generated.

Then the free stage turned out to be free in both directions. The cross-encoder is a local forward pass, so it costs no quota — and a stage that costs nothing is a stage nobody audits. It had been running since M3 on the strength of being obviously a good idea. Ablated out, the fused order scores higher at every depth on both slices. Before deleting it: on 60 narrative questions the two orderings disagree on 16, the fused order wins 10 and the reranker 6, and a paired exact test puts that at p = 0.45. A coin flip. So the finding is not “the reranker hurts” — it is that a stage given to the pipeline for free bought nothing measurable, and n = 60 cannot separate the two. Truncation is not the explanation either: only 5.8% of chunks exceed the model's 512-token window. It is domain — an MS MARCO web-passage model reading 10-K prose against a fusion that already carries the lexical signal. The reranker therefore stays on in the headline config and the ablation is committed beside it, because turning it off would lift the numbers on the only 150 questions that exist to judge them.

Both traces are captured in-process by a span processor attached to our own provider, so they are evidence about the graph's instrumentation rather than about whether Phoenix was up that afternoon — and they are captured --live, with the response cache off. Every prompt in the frozen set has already been answered, so a cached capture reports llm_calls: 0 and sub-millisecond model spans: true, since the counter counts hosted HTTP calls, but read out of a file it says the agent makes no model calls at all.

Verification and guardrails

The layer that lets you claim zero hallucinated figures without hand-waving.

Build

  • Numeric verifier: every derived figure recomputed in DuckDB from source facts
  • Citation resolver: a claim without a resolvable locator does not ship
  • Abstention guard on the final answer
  • Failure taxonomy tags written onto spans (retrieval_miss, router_wrong, grader_false_positive, synthesis_drift)

Definition of done

  • Hallucinated-number rate = 0 on the numeric slice — 0 of 133 figures, on every slice, all matched on the strict digit tier
  • 30 sampled answers: 100% of claims resolve to a real locator — 100% of 164 markers over all 150 answers, not a sample; 0 dangling, 0 unlocatable
  • Abstains on 10/10 unanswerable, and fires on <5% of answerable questions — 10/10, and 0.00% of 140 answerable
  • Failure taxonomy is queryable in Phoenix — a server-side filter per tag, wired to filing failures; the path that makes it work is below
duckdbpydanticarize-phoenix

If it breaksIf the guard rejects too many valid answers, switch it to log-and-flag rather than hard-block, and report the flag rate. A system that surfaces its own uncertainty still beats one that suppresses it.

What actually happenedEvery criterion cleared, the bail-out was never needed, and the most useful thing the gate produced was a list of bugs in itself. 0 hallucinated figures in 133, 100% of 164 citations resolving to a locator, 10/10 abstentions, and a flag rate of 0.00% on the 140 answerable questions — so hard-block costs zero answers and stays on. None of it calls a model: the verifier is arithmetic, regex and a DuckDB lookup, because an LLM-as-judge would be one unverified system checking another and the point is to have exactly one thing in the loop that cannot hallucinate.

The first six flags were all false positives, and all four causes were in the verifier. A multi-marker citation [2, 3, 5] whose digits were read as three hallucinated figures and whose sentence therefore looked uncited; the date a period ends read as two figures; a minus-signed loss compared against a profit; and every abstention checked against fact evidence it never claimed. Fixing them took narrative hallucination from 14.7% to 0.0% and the flag rate from 4.0% to 0.0%. A verifier written carefully and unit-tested still shipped four false positives, and the only reason they were caught is that six flags on 150 answers is few enough to read every one.

Zero flags proves nothing, so the guard was made to fire. All 116 real answers were corrupted four ways — bend a figure, cite past the end of the evidence, strip every marker, swap a figure for one from nowhere — and the verifier caught 426 of 427, while all 116 of 116 unmutated answers still passed. The single escape is a trial's phase number bent from 4 to 5.48 inside a qualitative sentence: a label, not a measurement. And the control found a hole the unit tests had not, which is the point of building one — the uncited-claim rule was figure-scoped, so a purely qualitative answer with every marker stripped passed vacuously, which is exactly the claim-without-a-locator this gate forbids.

The taxonomy criterion nearly passed by accident. Phoenix un-flattens OTel attribute keys into nested JSON and its filter language resolves only the bracket-chained form: attributes["filing"]["failure"]["kinds"] returns 70 spans, while attributes["filing.failure.kinds"] and attributes.filing.failure.kinds return zero — without raising. They parse, run, and come back empty, which reads exactly like nothing ever failed. An observability query whose broken state is indistinguishable from a clean run is worse than none, so filing failures cross-checks the per-tag filters against a tag-agnostic count and prints whether they agree.

Verification is off in the headline agent config. M6 ships as two new ones — agent-guarded and agent-flagged, the same check enforced and merely reported — rather than quietly moving M5's baseline. What the gate does not do is worth stating: it checks that a figure is in the evidence and that a citation points at something with a locator. It does not check that the evidence supports the sentence built around it, and it cannot — that is a semantic judgement, and the moment a model makes it, the one component that cannot hallucinate stops being that.

Gate rules

  • No gate advances on a claim. Every DoD item is a command that exits zero or a number you can print. If you cannot verify it, it is not done.
  • Tracing is on from the first commit. Retrofitting observability is the single most common reason these projects end up unexplainable.
  • The eval set freezes at M4 and gets a version tag. Adding a question later invalidates every earlier comparison — if you must, bump to v1.1 and re-run everything.
  • Commit results/*.json at every gate. The git history of your metrics is itself a portfolio artifact — it shows the project improving under measurement.
  • Every number in the README is regenerable by one documented command. A number you cannot reproduce is a number you cannot defend in an interview.
