# The gate going red

M8's second criterion asks for something stronger than a passing build: *"CI
provably fails on an injected regression — demonstrate it on a throwaway
branch."* A green check mark proves nothing on its own. A gate that has never
been seen to fail is indistinguishable from a gate that cannot.

This is the transcript. Branch `demo/gate-catches-a-regression`, commit
`6764753`, which carries the whole M8 change set plus one number moved by hand.

## The injection

```
$ git switch -c demo/gate-catches-a-regression
$ sed -i '46s/0.9875/0.8/' results/agent.json
$ git diff --stat
 results/agent.json | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

```diff
--- a/results/agent.json
+++ b/results/agent.json
@@ -43,7 +43,7 @@
    "name": "overall",
    "n": 150,
    "retrieval_n": 60,
-   "exact_match": 0.9875,
+   "exact_match": 0.8,
    "hit_rate": {
     "1": 0.15,
     "5": 0.4,
```

One line, and it is deliberately the *cheap* line. The 150 outcomes underneath
it are untouched — every answer the agent gave, every citation, every gold span
is exactly as it was. Only the headline in the scorecard has moved.

That is the shape the regression actually takes in a repository like this one.
Nobody edits four thousand lines of outcomes; a summary number goes stale, or
gets nudged, or is regenerated by code whose definition has drifted, and it
stops describing the run sitting directly beneath it. The interesting question
is whether anything notices.

Two of three check kinds fire, and they fire for different reasons, which is
the part worth reading closely:

**The floor** says the committed number is below a threshold someone wrote down
on purpose. This is the check that would catch an *honestly* worse run — a
model swap, a prompt edit, a retrieval change that quietly cost eighteen points
of numeric accuracy and got committed because the suite was still green.

**The rescore** says the committed number does not match what the committed
answers actually score. It rebuilt all 150 `Outcome` objects out of the same
file and ran today's metrics module over them, and got 0.9875. This is the
check that catches the thing a floor cannot: a number that is *wrong about its
own run*, whether because a hand edited it or because the code that computes it
changed underneath.

Note what stays green. The other five configurations are untouched and say so —
the gate localises the damage instead of going uniformly red. And the `agent`
**fingerprint** still passes, correctly: the configuration that produced this
run has not changed. It is the scorecard that lied, not the config, and the
report distinguishes those two failures rather than collapsing them into
"something is wrong".

## The suite

The same injection also takes the test suite down, because three tests in
`tests/test_gate.py` assert the gate is green on the *committed* results:

```
$ python -m pytest tests/test_gate.py
```

```
E       AssertionError: agent rescore: 150 outcomes re-scored overall.exact_match: file 0.8 -> now 0.9875
E         agent floor: exact_match 0.8000 >= 0.9500 the numeric slice is the headline claim

FAILED tests/test_gate.py::test_the_gate_passes_on_the_committed_results
FAILED tests/test_gate.py::test_the_gate_never_opens_a_socket
FAILED tests/test_gate.py::test_the_markdown_marks_failures_loudly
3 failed, 13 passed in 6.78s
```

Two belts, and they are not the same belt. `test_the_gate_passes_on_the_committed_results`
is the assertion that this repository's numbers are internally consistent right
now; `test_the_markdown_marks_failures_loudly` is the assertion that a failure
is *visible* — that `**FAIL**` appears in the rendered table, so a red run is
readable in a CI log without anyone re-deriving it. That second one failing here
is a slightly funny artefact: it asserts the committed table contains no
`**FAIL**`, so bending the data makes it fail by finding exactly the marker it
is there to guarantee gets printed.

## The other seven

The demonstration above moves one number by hand. Seven more injections live in
`tests/test_gate.py`, each staged into a sandbox copy of `results/` and each
asserted to be caught:

| injection | what the gate does |
|---|---|
| headline number dropped | the floor fails |
| a nested scorecard leaf edited | the rescore fails, naming the leaf |
| the config changed after the run that produced it | the fingerprint fails |
| an answer swapped for a wrong one | the rescore fails |
| a run marked `full_set: false` | refused outright, and *not scored at all* |
| a results file not committed | reported as missing, not skipped |
| a config name the repository does not have | reported as unknown |

The last three are the quiet ones. A gate that scores whatever files happen to
be present will pass on an empty directory, and a gate that scores a partial run
will report a flattering number computed over forty questions instead of a
hundred and fifty. Both are failures here, and both have a test.

And one negative control: `test_the_gate_never_opens_a_socket` monkeypatches
`socket.socket` to raise, then runs the whole gate. That is the property that
lets this job run on a pull request from a fork with no key, no corpus and no
Qdrant — and the property that would silently rot the first time someone made
the gate "just fetch one thing".

## Why there is no Actions run to link

This repository has no remote, so `.github/workflows/ci.yml` has never been
executed by GitHub. What is demonstrated above is the workflow's own command —
the `gate` job runs exactly `python -m filing.eval gate`, and CI fails on its
non-zero exit the same way this terminal did. When the repository is pushed, the
`demo/gate-catches-a-regression` branch is a ready-made red build; it is kept
unmerged for that purpose.
